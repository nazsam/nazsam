Chapter 03

Releases, upgrades, and rollbacks

Everything after the first install is built on that release record. Each time you change a value or move to a newer chart and run helm upgrade, Helm renders the new version, applies the difference to the cluster, and saves a new revision, version 2, then version 3, and so on. Running helm history myapp shows you the whole trail of what was deployed when.

Because every past revision is still stored in the cluster, helm rollback myapp 2 puts you back exactly where revision 2 was. That is the feature people fall in love with the first time an upgrade goes sideways at two in the morning. Helm keeps the last ten revisions by default and quietly prunes older ones, which you can change if you need a longer trail. And uninstalling a release removes the objects Helm created and, unless you ask it to keep the history, forgets the release as well.

Sharp edge: Your secrets end up in the release. The release Secret stores the fully rendered manifests, so any secret values you passed in are sitting inside it. Treat release storage as sensitive, keep plaintext secrets out of values files you commit to version control, and reach for a proper secrets tool when it matters. It is also why a release has a rough size ceiling of about one megabyte, which very large charts can bump into.
Explain like you are 10

A release is a saved game. Each upgrade saves a new slot (revision). Bad upgrade? Load revision 2 — you're back where you were in seconds, not rebuilding from scratch.

Try this scenario

2 AM rollback: New image causes crash loop. You run helm history payments-api — revision 3 is broken, revision 2 was fine. helm rollback payments-api 2. Pods recover in under a minute. Next day: fix the image tag in values and upgrade properly.
